## Finding 1: The Model editor cannot change or display the configured model
Recommendation: fix now

`app/src/generate/agent-slip.tsx:410-427, 459-474, 539-552` supplies only sampler objects for the Model part. Neither its base nor its draft contains the actual model or a way to select one, and the target line contains only the profile label, endpoint and URL. This does not deliver the first Done when line's inspection and editing of the active model/profile.

The apparent workaround silently fails: I used `nextTurnDraft` and `nextTurnEdits` to put `{"model":"writer-chosen-model"}` in Model with Profile default selected, then passed the edits to `sendNextTurn`. It returned `done` and saved that object in the profile default, but the actual request still contained `model: "original-model"`. `buildRequest` in `app/src/llm/client.ts:50-55` deliberately overwrites sampler.model with the backend profile's configured model. Add a real, scoped model edit to the session/default/send contract and show the effective model, with a test that checks the model actually sent. Keep the request builder's protection of unrelated structural fields.

## Finding 2: Ordinary query results have no clickable record or scene references
Recommendation: fix now

`app/src/agent/inspect.ts:314-340` only extracts named references from changed records and `trace` suspects. Successful read queries have no changes and, unless they are `trace`, no suspects. Their structured result data is never inspected. A real `show({ref:"actor:mara"})` returned `data.ref: "actor:mara"`, but `callNamed` returned `[]`; its slip therefore has no reference to open. The same omission applies to references returned by `touches`, `scenes` and `mentions`.

DESIGN.md's Tool trace part requires records and scenes named in a result to be references above the raw result. Extract those references from the supported query result shapes as well as mutation changes and trace suspects. Add component coverage that follows a normal query-result reference through `onOpen`; the existing multi-tool test includes `show` but checks links only for `trace`.

## Finding 3: Resuming a turn adds the writer's pause to a completed tool's duration
Recommendation: fix now

`app/src/agent/inspect.ts:80-91` treats the next call's start time as the previous call's completion time. The runner supports pausing between calls of one model response, so that interval includes time spent waiting for the writer, potentially across a reload.

I sent a response containing two `show` calls, paused after the first with `shouldPause`, advanced the injected clock by one hour, and resumed. Before the pause the first call showed 1 ms. After resume the same completed call showed 3,600,004 ms, although it had not run again. Persist a completion timestamp or elapsed duration per call when it finishes, and derive the display from that rather than the next call's start. Older records without sufficient timing information should show an unknown duration. Cover pause/resume in the duration test.

## Finding 4: Structured story-time results lose the prescribed time treatment
Recommendation: defer

`app/src/generate/agent-slip.tsx:244-248` renders every successful result as one unstyled JSON string. Consequently, story-time values in `show` or `span` results receive the same neutral treatment as all other fields, despite DESIGN.md requiring story dates and spans in the slip to use `time`. The report acknowledges this gap. A later typed result summary can apply the story-time treatment while retaining raw JSON for provenance; this does not block the usable inspector.
