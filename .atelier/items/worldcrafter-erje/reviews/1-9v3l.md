## Finding 1: checkRequest allows `tools: []`, which OpenAI answers with 400
Recommendation: defer
`buildRequest` omits an empty tool list (`client.ts:54`), and a test covers that. `toolsProblem` (`client.ts:165-184`) treats `tools: []` as valid when `tool_choice` is absent or `"auto"`. A chat body with `"tools": []` therefore passes `checkRequest` and is sent. OpenAI refuses an empty `tools` array; that is the class of 400 `checkRequest` was extended to catch. The runner will use `buildRequest`, so the hole is an edited request in the context viewer (tools live in the parameters JSON). Refuse `tools.length === 0` the same way the completion path already refuses any `tools` field.

## Finding 2: Synthesized tool-call ids restart at `call_0` on every response
Recommendation: defer
When a provider omits `id`, `ToolCallAssembly.result` (`parse.ts:184`) writes `call_${i}` from the slot index of that response. Two turns that both omit ids both produce `call_0`. `checkRequest` only matches results against the preceding assistant turn, so `send` still accepts the history, but a backend that matches `tool_call_id` globally in the chat template can bind the second result to the first call. OpenAI, OpenRouter and llama.cpp normally send ids; this is the fallback path. A per-client counter or a unique suffix would keep the fallback unique across the conversation.

## Finding 3: Completion.toolCalls order is first-seen, not provider index
Recommendation: no action
`byIndex` maps a provider `index` to the slot created when that index (or a new id at a known index) first appears (`parse.ts:153-163`). If a stream sends index 1 before index 0, `Completion.toolCalls` is `[call_1, call_0]` and `ToolCallDelta.index` is that slot, which is what the type comment promises (`types.ts:155`). Results are matched by id. Nothing to change unless a consumer wants OpenAI's index order.
